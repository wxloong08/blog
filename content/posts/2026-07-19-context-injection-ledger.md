> loongcli 开发笔记第六篇。起因是一场真实面试：我讲自己的"五层上下文压缩"，讲到一半把层背混了——投影是哪层、占位符是哪层、auto-compact 和 compact 是不是一层，当场心虚。回来当天把其中三层删了（-481 行）。删完才看清一件更大的事：**压缩根本不是上下文管理的主体，只是总账里的一小笔。**给未来的自己留两句话——上下文管理的正确问法不是"怎么压"，是**"谁在往模型眼前塞东西、塞在哪、多久变一次"**；还有一句更疼的：**这五层不是我设计的，是我压着自己的怀疑，从论坛照搬来的。**

## 一、框是别人给的，怀疑是自己压的

先交代五层的出身，这是全篇最疼的部分。"上下文管理 ≈ 五层压缩"这个框**不是我设计出来的，是我从论坛和博客的 Claude Code 逆向分析里照搬的**。Claude Code 闭源，所谓"源码分析"全是二手转述——但"人家扒过源码"这个光环足够亮，亮到我把自己的怀疑压了下去。

怀疑不是事后诸葛。两个证据：面试讲到一半我就意识到"这些层作用都重复了"——**但我没说出口，硬着头皮把错的讲完了**。压住怀疑的姿势，从照搬那天起一路保持到了面试现场；更早在 7 月初，我自己核对 Claude Code 的实际行为时就已经发现，**社区那套"N 层压缩"是把源码里的分类学当成了运行时架构，其中几层在 Claude Code 里就是死代码，活跃的层全是近窗口才触发的事件**。也就是说：我照搬的不是 Claude Code 的设计，是**别人对闭源系统的误读**；而且我在 7 月 2 日就知道了这一点，金字塔却又在我的代码库里活了 17 天。

两次怀疑，零次动作——第二次甚至是当着面试官的面，选择把错的讲完而不是停下来。第三篇复盘过这个等式里的成本模型错误（缓存时代删改历史反而贵 22 倍），但那次也只修了账本，没修对象、更没修态度——直到面试把我问穿，才承认：我讲不清五层，不是记性问题，是**这五层本来就不是一个自然的整体**——其中三层（投影、占位符、删远古）干的是同一件事的三种狠度，另外两层（入口截断、摘要）和它们根本不是一个物种。用"层"来组织认知，怎么背都背不顺；用别人误读出来的"层"来组织，就更背不顺了。

换一个单位，一切就顺了：**模型每一轮看到的 prompt，是十几个来源拼出来的；每个来源都是一次注入。**压缩只是其中唯一做"重写"的那笔，而重写恰恰是被实测证伪该少做的事。真正每天在管的，是注入。

## 二、注入总账

按 prompt 从头到尾，loongcli 现在的每一笔注入。三列信息：**是什么、多久变一次、为什么在这个位置**。

**前缀区**（系统提示装配，`prompts.py`，唯一排序原则：**越易变越靠后**）：

| # | 注入源 | 易变性 |
|---|---|---|
| 1 | 静态核心：身份/规则/工具 schema | 发版才变 |
| 2 | LOONG.md 项目指引 | 手写，极少变 |
| 3 | MCP 工具描述 | 配置变才变 |
| 4 | 技能清单 | 手动增删技能才变 |
| 5 | 记忆索引（MEMORY.md，索引不是全文） | 自动抽取，会话内会变 |
| 6 | 活跃计划 | 每完成一步就变 |
| 7 | 环境：cwd/日期/git 快照（带"这是快照"标签） | 每天/每会话必变 |

这个排序不是审美，是钱：前缀缓存从第一个不同的 token 起全部失效，易变内容每靠前一位，它的每次变化就多烧掉一段历史的缓存。第二篇量过这个量级——recall 从 position 1 挪到末尾，命中率 53% → 99%。

有一笔容易看漏：**工具 schema 也是注入**。技能清单曾经嵌在 skill 工具的 description 里——工具 schema 位于整条前缀的最前端，于是每装一个新技能，就把整条缓存从头打穿一次。发现之后把清单挪进了前缀区第 4 位（技能是手动增删的，比记忆索引稳定）。同一份信息，换个位置，付费模式完全不同。

**对话流区**（运行时注入，全部只追加、全部尽量靠尾）：

| # | 注入源 | 时机 |
|---|---|---|
| 8 | recall 召回（top-5 记忆） | user 消息前，紧贴末尾 |
| 9 | skill 触发注入 / skill() 全文拉取 | 输入命中触发词 / 模型主动调 |
| 10 | verify prompt（改码后强制验证） | 收尾被拦截时 |
| 11 | mailbox / 子任务完成通知 | 迭代边界 |
| 12 | 执行中插话（用户排队消息） | 迭代边界（最新一笔，上周加的） |
| 13 | 图片（read_file/MCP 截图） | 本轮工具序列完整落库后 |
| 14 | 入口截断 | **负注入**：工具结果进历史前先裁（8K/条、错误 16K、单轮 30K） |
| 15 | compact 摘要 | **唯一的重写**：逼近窗口才触发的保险丝 |

十五笔。原来叫"五层压缩"的东西，在这张账里只占两笔（14、15），而且一笔是"少塞点"、一笔是"实在塞不下了重写"——它们是账本的边角，不是主体。

## 三、从散点收成三条纪律

把十五笔放在一张纸上，规则自己浮出来了：

**位置纪律：越易变越靠后。**前缀区按跨会话易变性排序；对话流区一律尾部追加。度量：53% → 99%。

**改写纪律：中段永不改写。**历史只能追加，不能回头动——违反这条的三层（投影、占位符替换、删远古）已被探针实测处决（保前缀比删改便宜 22 倍、命中 98% vs 12%）。compact 是唯一豁免，且定位从"省钱手段"退役成"窗口保险丝"：jobhunter 在 loongcli 上跑了一个多月，一次都没触发。保险丝不熔断才是常态。

**预算纪律：常驻的必须 O(1)。**前缀区的每一 K 都是**每轮都付的房租**，所以常驻位只放索引：记忆是 MEMORY.md 索引（封顶 25KB）不是全文，技能是名字清单不是正文（两段式，正文按需拉取），MCP 眼下全量注入、规模化的路线也已经想清楚（清单进 prompt、schema 按需检索）。对话流区的注入只付一次，可以奢侈一点。

## 四、为什么这张账现在才算清

因为十五笔是十五个项目里各自长出来的：recall 是做记忆系统时加的，技能清单是做 skill 框架时加的，压缩是省钱焦虑时建的，插话是修 UX 时加的。每次都在解各自的局部问题，从来没人把它们放在同一张纸上。

**名字决定视角。**叫"压缩"的时候，我在省钱；叫"记忆"的时候，我在做检索；叫"上下文管理"的时候，我以为自己在管一个抽象的池子。直到统一叫"注入"，每个新功能的 review 问题才自动变成三连问：**塞在哪？多久变？付几次钱？**——上周做"执行中插话"就是第一个受益者，设计时直接按三连问定了"迭代边界 + 尾部 + 只付一次"，没有走弯路。

还有一个朴素的收口：所有这些子系统——记忆、技能、MCP、压缩、召回、插话——产出最终都坍缩进**同一个 messages 数组**。模型看不见你的架构图，它只看得见这个数组。管好这个数组，就是管好了一切；讲清这个数组，才算讲清了上下文管理。

## 可迁移的认知

1. **怀疑对上权威时，给怀疑一个便宜的验证出口，而不是投降。**这是本篇最贵的一条。我的怀疑两次都是对的（层作用重复；社区分析是误读），两次都被"人家分析过源码"压住。正确动作第二篇早就写过——判断让位于便宜的测量：一个探针几毛钱，比十七天的自我怀疑便宜得多。**尤其记住：闭源系统的一切"源码分析"都是二手转述，转述者把死代码当架构的概率不低。**
2. **上下文管理的单位不是"层"，是"注入源"。**层是实现的分类学，注入源才是问题的分类学——我背不住五层，是因为五层不是自然单位，更因为它是别人误读出来的单位。
3. **每笔注入过三连问：塞在哪（缓存断点）、多久变（易变性）、付几次钱（常驻房租 vs 一次性）。**这三问能在设计期拦住大部分上下文事故。
4. **统一命名是架构动作。**散点问题收进一个名字底下，规则才会自己浮现——"注入"这个名字值一次重构。
5. **模型的输入是唯一真相。**任何子系统的价值，最终都要在 messages 数组里兑现；审计这个数组（现在有 events.jsonl 记每轮 token 分布），比审计任何架构图都诚实。
